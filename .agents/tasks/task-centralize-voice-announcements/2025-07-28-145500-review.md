# Centralized TTS playback via admin panel

All voice announcements now funnel through the admin panel. Agent and TL panels no longer carry TTS infrastructure; they emit `voice-announce-request` over Socket.IO, the server relays to `admin-room`, and admin's new TTS stack plays the audio. The motivation is straightforward: admin is the only tab guaranteed to be open, so placing the speaker there eliminates missed announcements when agent/TL tabs are closed.

**Watch for:** Announcement flooding at the top of every hour when all connected agent + TL panels simultaneously fire their hourly review stats into one admin queue (confirmed). Duplicate playback if multiple admin tabs are open, since `admin-room` is a Socket.IO room with no occupancy limit (confirmed). No length or rate limiting on the relay path — any socket can push arbitrary text to admin's TTS queue (confirmed).

## High-level view

The server-side change is minimal: a single `voice-announce-request` handler that validates `text` is a non-empty string and forwards it to `admin-room`. No queueing, deduplication, or rate limiting happens server-side; all coordination lives in the admin client's TTS turn-lock mechanism.

The hourly scheduler remains on each agent/TL panel (it knows its own `agentId` and fetches its own stats), but instead of playing audio locally it fires multiple `voice-announce-request` messages per agent per hour-mark. With N agents and a TL connected, the admin queue receives 3-5+ messages from each at minute :00, all at once. The queue serializes them, but cumulative playback time may extend well past the hour.

Personal-feedback messages (justification confirmations, individual break warnings) that previously played only on the agent's own machine now broadcast through the admin speaker — a UX change that may not be intentional.

## Announcement storm at hour boundaries

The hourly review scheduler fires on every agent and TL panel independently (checked every 15 seconds, triggers at `:00` of hours 12-17). Each fires `announceDispositionStats()` followed by `announceTargetAndRanking()`, which together emit 3-5 separate `voice-announce-request` messages per panel (disposition summary, target, ranking, team ordering). With 10 agents online, the admin queue receives 30-50 chunks within seconds.

Each chunk takes 3-8 seconds of audio. A burst of 40 chunks means the speaker is busy for 2-4 minutes reciting everyone's stats in sequence. By the time it finishes, the information is stale and the next hour boundary is approaching.

Previously each agent's panel played only its own stats locally in parallel. Now everything converges on one serial output device. The architecture would benefit from either (a) server-side aggregation that composes one combined hourly announcement, or (b) staggering the per-agent announcements with random jitter.

## Duplicate playback with multiple admin tabs

```javascript
socket.on('join-admin', () => {
  socket.join('admin-room');   // no guard, no max occupancy
});
```

Every admin page load (including refreshes, multiple browser tabs, or multiple machines viewing admin) adds another socket to `admin-room`. When `voice-announce` is emitted to the room, every member plays it. The TTS turn lock partially mitigates this — if both tabs request a turn, only one gets it at a time — but both will eventually play the same message in sequence, doubling total announcements.

If the intent is exactly one speaker system, the server could track whether a TTS-capable admin is already in the room and skip additional members, or the client could coordinate via `BroadcastChannel`/`localStorage` to elect a single tab as speaker.

## Relay path has no input constraints

```javascript
socket.on('voice-announce-request', ({ text }) => {
  if (text && typeof text === 'string') {
    io.to('admin-room').emit('voice-announce', { text });
  }
});
```

No length cap (a 10 KB string would be chunked into ~50 segments by `_splitTTS`), no per-socket rate limit, and no authentication check. Any WebSocket connection — not just logged-in agents — can push text into the admin's audio queue.

In the current deployment context (internal CRM on a LAN) this is low risk, but worth noting as a hardening point. A simple `text.slice(0, 500)` and a per-socket cooldown (e.g., one message per 5 seconds) would cap exposure.

## Personal confirmations now broadcast on the admin speaker

When an agent submits a justification, the thank-you voice message (`'धन्यवाद। आपका स्पष्टीकरण दर्ज कर लिया गया है।'`) previously played on that agent's machine as personal feedback. It now goes through the admin speaker. Same for break warnings ("your break has only 5 minutes left") — these were per-agent nudges that now announce on a shared speaker, potentially in earshot of the entire office.

If not intentional, these personal-feedback messages could use `speechSynthesis` locally on the agent panel while only routing team-wide announcements through the server relay.
